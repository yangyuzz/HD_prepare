모듈 5: 영상(Video) 분석 기초

동영상을 프레임 단위로 읽고 쓰는 방법과, 고정 카메라 영상에서 움직임을 찾고 그 방향과 크기를 구하는 전통 기법을 다루는 덱입니다. 딥러닝 없이도 OpenCV만으로 할 수 있는 영상 분석의 기본기를 익히는 것이 목표입니다.

동영상의 구조

설명 동영상 분석은 결국 이미지 여러 장을 차례로 처리하는 일입니다. 이 장에서는 동영상이 어떻게 이루어져 있는지(프레임, FPS, 해상도, 코덱), 파일과 카메라에서 프레임을 어떻게 꺼내고 다시 저장하는지, 그리고 실시간으로 처리하려면 시간이 얼마나 주어지는지를 봅니다.

동영상은 프레임의 연속

  • 프레임(frame): 동영상을 이루는 정지 이미지 한 장. 이미지와 똑같은 배열 (H x W x 3)
  • 프레임을 빠르게 이어 보여 주면 사람 눈에는 움직임으로 보인다
  • 동영상 처리 = 프레임마다 이미지 처리를 반복하는 것
  • 프레임마다 번호(0, 1, 2, ...)가 있고, 번호는 시간과 대응한다

설명 동영상은 특별한 데이터가 아니라 사진을 아주 빠르게 넘기는 책장 넘기기 그림(플립북)과 같습니다. 각 장을 프레임이라고 부르고, OpenCV로 읽으면 프레임 하나가 이미지 배열과 똑같은 NumPy 배열로 나옵니다. 그래서 이미지에 쓰던 흑백 변환, 이진화, 모폴로지, 딥러닝 추론을 프레임마다 그대로 적용할 수 있습니다. 동영상에만 있는 새로운 정보는 "이웃한 프레임 사이의 변화", 즉 시간 축입니다.

예상 질문 Q: 동영상 파일 안에 프레임 이미지가 하나하나 그대로 들어 있나요? A: 아닙니다. 파일 안에는 압축된 데이터가 들어 있고, 읽을 때 코덱이 압축을 풀어 프레임 배열을 만들어 줍니다.

주의 OpenCV로 읽은 프레임은 이미지와 마찬가지로 BGR 순서입니다. matplotlib으로 보여 줄 때 색이 이상하면 RGB로 바꿔야 합니다.

FPS와 시간

  • FPS (Frames Per Second): 1초에 담긴 프레임 수
  • 시간과 프레임 번호의 변환: 시간(초) = 프레임 번호 / FPS, 프레임 번호 = 시간 x FPS
  • 동영상 길이(초) = 전체 프레임 수 / FPS
  • 정보 읽기: cap.get(cv2.CAP_PROP_FPS), cv2.CAP_PROP_FRAME_COUNT

설명 FPS는 1초 동안 몇 장의 사진을 넘기는지를 뜻합니다. 30 FPS 동영상이라면 90번째 프레임은 90을 30으로 나눈 3초 지점에 있습니다. 반대로 "10초 지점의 장면"을 찾으려면 10 x 30 = 300번 프레임을 보면 됩니다. 이 변환은 영상에서 사건이 일어난 시각을 기록하거나, 특정 구간만 잘라 낼 때 계속 쓰입니다.

예상 질문 Q: FPS가 높으면 무조건 좋은가요? A: 빠른 움직임을 더 촘촘히 담을 수 있지만, 같은 길이에 프레임이 많아져 파일이 커지고 처리할 양도 늘어납니다. 용도에 맞게 고릅니다.

주의 FPS가 29.97처럼 정수가 아닐 수 있고, 스마트폰 영상은 프레임 간격이 일정하지 않은 가변 프레임(VFR)인 경우도 있습니다. 이때 파일이 알려 주는 FPS와 전체 프레임 수는 근삿값일 수 있습니다. 카메라나 스트림은 전체 프레임 수가 정해져 있지 않습니다(값이 0이나 -1로 나오는 경우가 있으며 백엔드에 따라 다름, 버전 확인).

해상도와 데이터 양

  • 해상도(resolution): 프레임의 가로 x 세로 픽셀 수. 예: 1920 x 1080 (Full HD), 1280 x 720 (HD)
  • 압축하지 않은 프레임 한 장 = 가로 x 세로 x 3 바이트
  • 1920 x 1080 x 3 = 약 6.2MB, 30 FPS면 1초에 약 187MB
  • 그래서 파일에는 압축해서 저장하고, 분석할 때는 크기를 줄여 처리하는 경우가 많다

설명 해상도는 사진 한 장이 몇 개의 점(픽셀)으로 이루어졌는지입니다. 컬러 픽셀 하나는 B, G, R 세 값이고 각각 1바이트이므로, Full HD 프레임 한 장은 압축하지 않으면 약 6MB입니다. 1초에 30장이면 약 187MB가 되니, 압축 없이 저장하는 것은 현실적이지 않습니다. 분석할 때도 같은 이유로 프레임을 줄여서(resize) 처리하는 경우가 많습니다. 숫자는 곱셈으로 직접 계산해 보여 주면 학생들이 바로 납득합니다.

예상 질문 Q: 해상도를 줄이면 분석 결과가 나빠지지 않나요? A: 작은 물체나 세밀한 부분은 놓칠 수 있습니다. 대신 처리 속도가 빨라지므로, 찾으려는 대상의 크기를 보고 줄일 정도를 정합니다.

주의 OpenCV에서 이미지 배열의 모양은 (세로, 가로, 채널)이지만, 해상도를 말하거나 함수에 크기를 넘길 때는 보통 (가로, 세로) 순서입니다. 순서를 헷갈리기 쉽습니다.

코덱과 컨테이너

코덱 (codec)
  • 프레임을 압축하고 푸는 방식
  • 예: H.264, MJPG(Motion JPEG), MPEG-4
  • 4글자 코드 FourCC로 지정 ('mp4v', 'MJPG')
컨테이너 (container)
  • 압축된 데이터를 담는 파일 형식
  • 예: .mp4, .avi, .mkv
  • 영상, 소리, 정보(FPS, 길이)를 함께 담는다

설명 컨테이너는 택배 상자, 코덱은 상자 안의 물건을 압축 포장한 방법이라고 비유하면 쉽습니다. 확장자 .mp4는 상자의 종류일 뿐이고, 안의 영상이 H.264로 압축됐는지 MPEG-4로 압축됐는지는 따로 정해집니다. MJPG는 프레임마다 JPEG 사진처럼 따로 압축하므로 구조가 단순하지만 파일이 큽니다. H.264는 이웃한 프레임 사이의 차이를 이용해 압축하므로 파일이 훨씬 작습니다.

예상 질문 Q: 같은 .mp4 파일인데 어떤 컴퓨터에서는 열리고 어떤 곳에서는 안 열리는 이유는 무엇인가요? A: 상자(mp4)는 같아도 안의 코덱을 풀 수 있는 프로그램이 그 컴퓨터에 없으면 열 수 없습니다.

주의 어떤 코덱으로 저장할 수 있는지는 OpenCV가 어떻게 빌드됐는지(FFmpeg 포함 여부 등)에 따라 다릅니다. 특정 코덱이 된다고 단정하지 말고 실습 환경에서 확인합니다(버전 확인).

카메라 입력

동영상 파일
파일 경로를 넘긴다
  • VideoCapture("a.mp4")
USB 카메라
장치 번호를 넘긴다
  • VideoCapture(0)
IP 카메라
스트림 주소(RTSP)를 넘긴다
  • VideoCapture("rtsp://…")
  • 입력이 달라도 프레임을 꺼내는 방법(read)은 같다
  • 카메라와 스트림은 끝이 없는 입력이다. 처리가 늦으면 지연이 쌓인다

설명 cv2.VideoCapture는 입력의 종류를 가리지 않는 수도꼭지와 같습니다. 파일 경로를 주면 파일에서, 숫자 0을 주면 컴퓨터에 연결된 첫 번째 카메라에서, rtsp로 시작하는 주소를 주면 네트워크 카메라에서 프레임을 받아 옵니다. RTSP(Real Time Streaming Protocol)는 CCTV 같은 IP 카메라가 영상을 네트워크로 보낼 때 흔히 쓰는 방식입니다. 어느 쪽이든 프레임을 꺼내는 코드는 같으므로, 파일로 개발하고 나중에 카메라로 바꾸는 방식이 편합니다.

예상 질문 Q: Colab에서 제 노트북 컴퓨터의 웹캠을 VideoCapture(0)으로 열 수 있나요? A: 안 됩니다. Colab 코드는 원격 서버에서 실행되므로 학생 컴퓨터의 카메라가 보이지 않습니다. 브라우저의 카메라를 쓰려면 JavaScript를 이용한 별도 방법이 필요하므로, 실습은 동영상 파일로 합니다.

주의 카메라나 스트림은 프레임이 계속 들어옵니다. 처리가 들어오는 속도보다 느리면 버퍼에 프레임이 쌓여 화면이 점점 과거를 보여 주게 됩니다. 처리 예산 이야기와 연결해서 설명합니다.

cap = cv2.VideoCapture("input.mp4")
while cap.isOpened():
    ok, frame = cap.read()
    if not ok: break        # 끝에 도달하거나 읽기 실패
    # 프레임 처리
cap.release()

설명 거의 모든 동영상 프로그램은 이 반복문 하나로 이루어집니다. 프레임 한 장을 읽고, 처리하고, 결과를 보여 주거나 저장한 뒤, 다음 프레임을 읽습니다. read()는 성공 여부와 프레임 두 가지를 돌려주는데, 동영상이 끝나면 성공 여부가 False가 되므로 반복을 멈춥니다. 다 쓰고 나면 release()로 파일이나 카메라를 놓아 줍니다.

예상 질문 Q: 화면에 동영상을 띄우려면 어떻게 하나요? A: 내 컴퓨터에서는 cv2.imshow와 cv2.waitKey로 창에 띄웁니다. Colab에서는 창을 띄울 수 없으므로 결과를 동영상 파일로 저장한 뒤 재생하거나, 몇 프레임만 이미지로 보여 줍니다.

주의 읽기 실패를 확인하지 않으면 마지막에 빈 프레임(None)을 처리하다 오류가 납니다. 또 Colab 환경에서는 cv2.imshow를 쓸 수 없어 오류가 나니 학생들에게 미리 알려 줍니다.

결과를 동영상으로 저장

fourcc = cv2.VideoWriter_fourcc(*"mp4v")
out = cv2.VideoWriter("out.mp4", fourcc, fps, (w, h))
out.write(frame)      # 루프 안에서 프레임마다
out.release()

VideoWriter에 준 크기 (가로, 세로)와 실제 프레임 크기가 다르면 파일이 비거나 열리지 않는다

설명 저장은 읽기의 반대입니다. 파일 이름, 코덱(FourCC), FPS, 프레임 크기 네 가지를 정해 VideoWriter를 만들고, 루프 안에서 처리한 프레임을 write로 한 장씩 넣습니다. 끝나면 release를 호출해야 파일이 제대로 마무리됩니다. FPS는 보통 원본 동영상의 FPS를 그대로 써서 재생 속도가 같게 합니다.

예상 질문 Q: 저장했는데 파일 크기가 아주 작고 재생이 안 됩니다. 왜 그런가요? A: 가장 흔한 원인은 크기 불일치입니다. 처리 중에 프레임 크기를 줄였거나 흑백으로 바꿨다면 VideoWriter에 준 크기와 컬러 여부도 그에 맞춰야 합니다.

주의 흑백(1채널) 프레임을 저장할 때는 컬러 여부 인자를 False로 주거나 3채널로 바꿔서 넣어야 합니다. 또 mp4v로 저장한 파일은 브라우저에서 재생되지 않을 수 있고, 브라우저 친화적인 H.264(avc1)는 OpenCV 빌드에 따라 지원되지 않을 수 있습니다(버전 확인).

실시간 처리 예산

약 33ms
30 FPS에서 프레임 1장에 쓸 수 있는 시간 (1000 / 30)
약 17ms
60 FPS에서 프레임 1장에 쓸 수 있는 시간 (1000 / 60)
  • 읽기 + 처리 + 표시를 합친 시간이 예산 안에 들어야 실시간이다
  • 넘치면: 해상도 줄이기, N 프레임마다 처리, 가벼운 모델 쓰기

설명 30 FPS 카메라는 약 33ms마다 새 프레임을 줍니다. 그러니 한 프레임을 읽고 처리하고 화면에 그리는 데 33ms보다 오래 걸리면 처리가 들어오는 속도를 따라가지 못합니다. 이것을 "프레임당 시간 예산"이라고 부르면 이해하기 쉽습니다. 예산을 넘을 때는 프레임을 작게 줄이거나, 모든 프레임이 아니라 몇 장마다 한 번씩만 처리하거나, 더 가벼운 모델을 고릅니다.

예상 질문 Q: 저장된 동영상 파일을 분석할 때도 예산을 지켜야 하나요? A: 파일은 기다려 주므로 느려도 결과는 같고 시간만 더 걸립니다. 예산이 중요한 것은 카메라처럼 실시간으로 들어오는 입력입니다.

주의 여기 나온 33ms, 17ms는 단순 나눗셈입니다. 특정 모델이 몇 ms 걸린다는 수치는 장비마다 다르므로 실습 환경에서 직접 재 보게 하고, 숫자를 단정해서 말하지 않습니다.

프레임 샘플링으로 학습 데이터 만들기

  • 이웃한 프레임은 거의 같다. 모든 프레임을 쓰면 비슷한 이미지만 많아진다
  • N 프레임마다 1장 또는 일정 시간마다 1장씩 이미지로 저장한다
  • 학습/검증 분할은 동영상 단위로 나눈다

같은 동영상의 프레임이 학습과 검증에 섞이면 검증 점수가 실제보다 좋게 나온다

설명 동영상은 Object Detection이나 분류 모델의 학습 데이터를 모으기 좋은 재료입니다. 하지만 30 FPS 영상에서 붙어 있는 프레임은 거의 같은 사진이라, 전부 저장하면 라벨링할 양만 늘고 다양성은 늘지 않습니다. 그래서 30프레임마다 한 장(1초에 한 장)처럼 간격을 두고 뽑습니다. 간격은 장면이 얼마나 빨리 바뀌는지를 보고 정합니다.

예상 질문 Q: 학습/검증을 왜 동영상 단위로 나눠야 하나요? A: 같은 영상에서 1초 간격으로 뽑은 두 장은 거의 같은 장면입니다. 하나는 학습에, 하나는 검증에 들어가면 모델은 사실상 본 문제를 다시 푸는 셈이라 점수가 부풀려집니다. 이것을 데이터 누수(data leakage)라고 합니다.

주의 시간 간격으로 뽑을 때는 FPS를 이용해 프레임 번호로 바꿉니다. 가변 프레임 영상에서는 간격이 정확히 일정하지 않을 수 있습니다.

[실습] 동영상 읽고 쓰기

Colab 열기 (준비 중)

이 실습이 다루는 개념:

1동영상 정보
FPS, 프레임 수, 해상도, 길이
2처리 루프
프레임 단위 읽기와 처리
3동영상 저장
코덱, FPS, 크기 지정
4프레임 샘플링
N 프레임마다 이미지 저장

설명 동영상 파일의 FPS, 프레임 수, 해상도를 읽어 길이를 직접 계산해 보고, 프레임마다 흑백 변환이나 글자 표시를 한 뒤 결과를 동영상으로 저장해 재생하는 실습입니다. 학생들이 볼 것은 세 가지입니다. 계산한 길이가 실제 재생 시간과 맞는지, 저장한 동영상이 원본과 같은 속도로 재생되는지, 샘플링 간격을 바꾸면 저장되는 이미지 수가 어떻게 달라지는지입니다.

주의 실행 팁: 이 실습은 CPU 런타임으로 충분합니다. 패키지를 설치하는 셀이 있으면 설치 후 런타임을 다시 시작하라는 안내가 나올 수 있으니 따르게 합니다. 동영상 파일 경로가 틀리면 오류 없이 프레임을 하나도 읽지 못하므로, 결과가 비어 있으면 먼저 파일 경로와 열기 성공 여부를 확인하게 합니다. 자세한 진행은 노트북의 설명 셀과 주석에 있습니다.

움직임 검출

설명 고정된 카메라 영상에서 "무엇인가 움직였다"는 것을 찾는 방법을 다룹니다. 이웃 프레임끼리 빼는 가장 단순한 방법에서 시작해, 배경을 따로 기억해 두고 비교하는 배경 차분, 그리고 결과 마스크를 정리해 박스로 만드는 과정까지 봅니다. 이진화, 모폴로지, 윤곽선 같은 이미지 처리 기법이 그대로 쓰입니다.

프레임 차분 (Frame Differencing)

  • 고정 카메라에서 배경은 그대로이고 움직인 곳만 픽셀 값이 바뀐다
  • 이전 프레임과 현재 프레임의 차이: cv2.absdiff(prev, curr)
  • 차이가 임계값보다 크면 255인 움직임 마스크를 만든다
  • 보통 흑백으로 바꾸고 블러로 잡음을 줄인 뒤 뺀다

설명 틀린 그림 찾기와 같은 원리입니다. 카메라가 고정돼 있으면 벽이나 바닥 같은 배경은 두 프레임에서 거의 같은 값이고, 사람이 지나간 자리만 값이 달라집니다. 두 프레임을 픽셀마다 빼서 절댓값을 구하면 바뀐 곳만 밝게 남고, 여기에 이진화를 적용하면 움직임 마스크가 됩니다. 센서 잡음 때문에 가만히 있는 곳도 값이 조금씩 흔들리므로, 블러를 먼저 적용하고 임계값으로 작은 차이를 걸러 냅니다.

예상 질문 Q: 그냥 빼면 되지 왜 absdiff를 쓰나요? A: 이미지 배열은 0~255의 부호 없는 정수(uint8)라서 그냥 빼면 음수가 되는 곳에서 값이 크게 뒤집혀 버립니다. absdiff는 차이의 절댓값을 안전하게 구해 줍니다.

주의 임계값이 너무 낮으면 잡음까지 움직임으로 잡히고, 너무 높으면 천천히 움직이는 물체를 놓칩니다. 정답 값은 없고 영상을 보며 정합니다.

프레임 차분의 특징

장점
  • 계산이 아주 간단하고 빠르다
  • 배경을 따로 학습할 필요가 없다
  • 조명이 서서히 바뀌어도 바로 따라간다
한계
  • 물체의 가장자리만 잡히고 속이 빈다
  • 물체가 멈추면 사라진다
  • 빠른 물체는 이전·현재 위치가 두 번 잡힌다

설명 프레임 차분은 바로 직전 프레임만 비교하므로 준비가 필요 없고 빠릅니다. 하지만 비교 대상이 "직전 모습"이라는 점 때문에 한계가 생깁니다. 색이 고른 상자가 오른쪽으로 조금 움직이면, 두 프레임에서 상자가 겹치는 가운데 부분은 값이 같아 차이가 0이 되고, 앞뒤 가장자리만 남습니다. 또 사람이 멈춰 서면 두 프레임이 같아져 마스크에서 사라집니다.

예상 질문 Q: 속이 비는 문제는 어떻게 해결하나요? A: 마스크에 닫기(closing)나 팽창을 적용해 어느 정도 메울 수 있고, 근본적으로는 "움직이기 전 배경"과 비교하는 배경 차분을 씁니다.

주의 빠른 물체가 두 번 잡히는 현상은 이전 위치(물체가 떠난 자리)도 값이 바뀌었기 때문입니다. 마스크의 덩어리 수를 물체 수로 바로 세면 틀릴 수 있습니다.

배경 차분 (Background Subtraction)

  • 배경 모델(background model): 움직이는 물체가 없을 때의 장면을 기억한 이미지
  • 현재 프레임과 배경 모델의 차이로 전경(foreground)을 찾는다
  • 배경은 고정이 아니라 프레임이 들어올 때마다 조금씩 갱신한다
  • 갱신 예: 배경 = (1 - α) x 배경 + α x 현재 프레임 (이동 평균)

설명 배경 차분은 "평소 모습"을 기억해 두고 지금 모습과 비교하는 방법입니다. 매일 보는 사무실 사진을 머릿속에 갖고 있다가 처음 보는 사람이 있으면 알아차리는 것과 같습니다. 직전 프레임이 아니라 배경과 비교하므로, 물체 전체가 전경으로 잡히고 잠깐 멈춰도 바로 사라지지 않습니다. 해가 지면서 밝기가 바뀌는 것처럼 배경도 변하므로, 새 프레임을 조금씩 섞어 배경을 갱신합니다.

예상 질문 Q: 처음 배경은 어떻게 얻나요? A: 첫 프레임을 배경으로 시작하거나, 처음 몇십~몇백 프레임을 보며 배경을 학습합니다. 시작할 때 물체가 화면에 있으면 한동안 그 물체가 배경에 섞여 잘못된 결과가 나올 수 있습니다.

주의 수식의 α는 학습률(갱신 속도)입니다. OpenCV에는 이 이동 평균을 구하는 cv2.accumulateWeighted가 있고, MOG2 같은 배경 차분기는 갱신을 내부에서 알아서 합니다.

갱신 속도의 균형

빠르게 갱신 (α 큼)
  • 조명 변화를 빨리 따라간다
  • 천천히 움직이거나 멈춘 물체가 빨리 배경에 묻힌다
느리게 갱신 (α 작음)
  • 물체가 오래 전경으로 남는다
  • 조명이 바뀌면 화면 전체가 한동안 전경으로 잡힌다

설명 갱신 속도는 "얼마나 빨리 새것에 익숙해지느냐"입니다. 빨리 익숙해지면 조명이 바뀌어도 금방 적응하지만, 문 앞에 놓인 택배 상자도 금방 "원래 있던 것"으로 받아들입니다. 느리게 익숙해지면 상자를 오래 알아채지만, 구름이 끼어 화면이 어두워지면 한동안 화면 전체를 이상하다고 판단합니다. 어느 쪽이 맞는지는 무엇을 찾고 싶은지에 따라 다릅니다.

예상 질문 Q: 적당한 값은 얼마인가요? A: 정해진 값은 없습니다. 영상의 조명 변화 속도와 물체가 머무는 시간을 보고 정합니다. OpenCV의 배경 차분기는 기억할 프레임 수(history)나 학습률 인자로 이 속도를 조절합니다.

주의 MOG2와 KNN의 apply에 학습률을 주지 않으면 자동으로 정해지고, 0을 주면 배경을 갱신하지 않습니다. 인자의 정확한 동작은 버전 확인이 필요합니다.

MOG2와 KNN 배경 차분기

MOG2 (Mixture of Gaussians)
픽셀마다 값의 분포를 가우시안 여러 개로 기억한다. 흔들리는 나뭇잎처럼 배경이 여러 모습이어도 배경으로 본다
KNN
픽셀마다 최근 값들을 표본으로 기억하고, 새 값과 가까운 표본이 충분하면 배경으로 본다
bg = cv2.createBackgroundSubtractorMOG2(detectShadows=True)
fg_mask = bg.apply(frame)   # 프레임마다 호출: 전경 마스크 + 배경 갱신

설명 단순 이동 평균은 픽셀마다 배경값을 하나만 기억합니다. 그런데 바람에 흔들리는 나뭇잎이나 물결이 있는 곳은 배경 자체가 두세 가지 모습을 오갑니다. MOG2는 픽셀마다 "자주 나오는 값의 무리"를 여러 개 기억해서, 그중 하나에 가까우면 배경으로 판단합니다. KNN은 최근에 본 값들을 그대로 표본으로 두고, 새 값과 비슷한 표본이 충분히 많으면 배경으로 봅니다. 두 방법 모두 apply를 부를 때마다 전경 마스크를 돌려주고 배경 모델도 갱신합니다.

예상 질문 Q: MOG2와 KNN 중 무엇을 써야 하나요? A: 영상에 따라 결과가 다릅니다. 둘 다 만드는 코드가 한 줄이므로 같은 영상에 둘 다 적용해 마스크를 비교해 보고 고르는 것이 좋습니다.

주의 OpenCV 문서에 따르면 MOG2는 Zivkovic(2004, 2006)의 적응형 가우시안 혼합 모델, KNN은 Zivkovic과 van der Heijden(2006)의 방법에 기반합니다. history, varThreshold 같은 인자의 기본값은 버전 확인이 필요합니다. 여기서 KNN은 분류 알고리즘 k-최근접 이웃과 같은 발상이지만 학습된 분류기가 아닙니다.

그림자 처리

  • 물체의 그림자도 배경과 값이 달라 전경으로 잡히기 쉽다
  • MOG2와 KNN은 그림자 검출을 켜면 그림자를 회색 값으로 따로 표시한다
  • 그림자 = 배경보다 어둡지만 색 성분은 비슷한 픽셀
  • 그림자를 빼려면 마스크에 임계값을 한 번 더 적용해 흰색(255)만 남긴다

설명 햇빛 아래 사람이 걸어가면 그림자도 함께 움직이고, 배경 차분은 그림자까지 전경으로 잡습니다. 그러면 사람 박스가 그림자만큼 길게 늘어납니다. 그림자는 배경을 어둡게 만들 뿐 색 자체는 크게 바꾸지 않는다는 성질이 있어서, 이를 이용해 그림자 픽셀을 구분합니다. MOG2는 그림자 검출을 켜면 전경은 255, 그림자는 회색, 배경은 0으로 표시한 마스크를 돌려줍니다.

예상 질문 Q: 그림자를 아예 안 잡게 할 수는 없나요? A: 그림자 검출을 끄면 그림자가 전경(255)에 섞여 나옵니다. 켜 두고 임계값으로 회색 부분만 버리는 것이 보통입니다.

주의 그림자 표시 값은 기본이 127로 알려져 있지만 바꿀 수 있는 인자입니다(버전 확인). 진한 그림자나 물체 색이 배경과 비슷한 경우에는 그림자와 물체가 잘못 구분될 수 있습니다.

임계값으로 255만 남김

설명 배경 차분이 준 마스크는 그대로 쓰기 어렵습니다. 여기저기 작은 흰 점(잡음)이 있고, 사람 몸 안에도 구멍이 뚫려 있기 때문입니다. 이진화와 모폴로지 도구로 정리합니다. 열기로 작은 점을 지우고, 닫기나 팽창으로 구멍을 메운 뒤, 윤곽선을 찾아 덩어리마다 박스를 그립니다. 면적이 너무 작은 덩어리는 잡음으로 보고 버립니다. OpenCV 함수로는 윤곽선 찾기에 cv2.findContours, 면적 계산에 cv2.contourArea, 감싸는 사각형에 cv2.boundingRect를 씁니다.

예상 질문 Q: 커널 크기와 면적 기준은 어떻게 정하나요? A: 찾으려는 물체가 화면에서 몇 픽셀 정도인지를 기준으로 정합니다. 사람이 화면에서 크게 보이는 영상과 멀리 작게 보이는 영상은 값이 다릅니다.

주의 사람 두 명이 붙어 걸으면 덩어리 하나로 합쳐져 박스도 하나가 됩니다. 반대로 한 사람이 둘로 쪼개지기도 합니다. 배경 차분의 박스 개수가 곧 물체 개수는 아니라는 점을 짚어 줍니다.

움직임만 알 뿐, 사람인지 차인지는 모른다

배경 차분은 고정 카메라를 전제로 한다

설명 배경 차분은 "배경은 변하지 않고, 바뀐 것은 물체다"라는 가정 위에 서 있습니다. 이 가정이 깨지는 상황이 바로 한계입니다. 불이 켜지거나 카메라가 바람에 흔들리면 배경 자체가 바뀌어 화면 전체가 전경이 됩니다. 주차한 차처럼 오래 멈춘 물체는 결국 배경으로 학습되어 사라집니다. 또 배경 차분은 움직였다는 사실만 알려 줄 뿐 그것이 무엇인지는 알려 주지 않습니다.

예상 질문 Q: 그럼 실제 서비스에서는 배경 차분을 안 쓰나요? A: 학습 데이터 없이 바로 쓸 수 있고 가벼워서 여전히 씁니다. 예를 들어 움직임이 있을 때만 Object Detection 모델을 돌려 연산을 아끼는 식으로 함께 쓰기도 합니다.

주의 카메라가 움직이는 영상(드론, 차량 블랙박스, 손에 든 휴대폰)에는 이 방법을 그대로 쓸 수 없습니다. 이런 경우 카메라 자체의 움직임을 먼저 보정하거나 다른 방법을 씁니다.

Optical Flow

설명 배경 차분은 "어디가 움직였나"를 알려 줍니다. Optical Flow는 한 걸음 더 나아가 "어느 방향으로 얼마나 움직였나"를 구합니다. 이 장에서는 Optical Flow가 기대는 가정, 특징점만 따라가는 Lucas-Kanade 방법, 모든 픽셀의 움직임을 구하는 Farneback 방법, 그리고 결과를 색으로 보여 주는 방법과 응용을 봅니다.

Optical Flow란

  • 이웃한 두 프레임 사이에서 픽셀이 어디로 얼마나 움직였는지 나타낸 벡터
  • 픽셀 (x, y)의 움직임 = (u, v): 가로 u픽셀, 세로 v픽셀 이동
  • 단위는 픽셀 / 프레임
  • 배경 차분이 "어디가 바뀌었나"라면, Optical Flow는 "어떻게 움직였나"

설명 Optical Flow는 화면 위에 그린 화살표들이라고 생각하면 됩니다. 각 화살표는 "이 점이 다음 프레임에서 이쪽으로 이만큼 움직였다"를 나타냅니다. 가로 이동량 u와 세로 이동량 v 두 숫자로 화살표 하나를 표현합니다. 이 화살표를 모으면 사람이 왼쪽으로 걷는지, 차가 어느 방향으로 달리는지, 카메라가 흔들렸는지 알 수 있습니다.

예상 질문 Q: 이 이동량이 실제 미터 단위 속도인가요? A: 아닙니다. 화면 위에서 몇 픽셀 움직였는지입니다. 실제 속도로 바꾸려면 FPS와 함께 픽셀 하나가 실제 몇 미터인지 같은 추가 정보가 필요합니다.

주의 Optical Flow는 화면에 보이는 밝기 패턴의 움직임입니다. 물체의 실제 3차원 움직임과 항상 같지는 않습니다. 예를 들어 회전하는 이발소 간판의 줄무늬는 실제로는 옆으로 도는데 화면에서는 위로 올라가는 것처럼 보입니다.

밝기 항상성 가정

  • 밝기 항상성(brightness constancy): 같은 점은 움직여도 밝기가 같다
    • I(x, y, t) = I(x + u, y + v, t + 1)
  • 작은 움직임: 프레임 사이 이동이 작다고 가정하고 식을 근사한다
    • Ix·u + Iy·v + It = 0 (Ix, Iy: 공간 기울기, It: 시간 변화)
  • 식은 1개, 모르는 값은 u, v 2개 → 추가 가정이 필요하다

설명 컴퓨터는 "이 점이 저 점으로 갔다"는 것을 어떻게 알까요? 기본 가정은 "움직여도 그 점의 밝기는 그대로다"입니다. 그래서 다음 프레임에서 같은 밝기를 가진 곳을 찾으면 그곳이 이동한 위치가 됩니다. 움직임이 작다고 가정하면 이 조건을 기울기(밝기가 옆으로 얼마나 변하는지)와 시간 변화로 이루어진 간단한 식 하나로 바꿀 수 있습니다. 문제는 식은 하나인데 구할 값은 u, v 두 개라서, 픽셀 하나만 보고는 답이 정해지지 않는다는 점입니다.

예상 질문 Q: 조명이 바뀌면 어떻게 되나요? A: 가정이 깨지므로 결과가 틀어집니다. 밝기가 바뀐 것을 움직임으로 착각할 수 있습니다.

주의 수식은 이해를 돕는 정도로만 보여 주고 유도 과정(테일러 근사)에 시간을 많이 쓰지 않아도 됩니다. 핵심은 "가정 두 개(밝기 그대로, 움직임 작음)"와 "식이 하나 모자라다"입니다.

조리개 문제 (Aperture Problem)

  • 작은 창으로 직선 경계만 보면, 경계를 따라 미끄러지는 움직임은 보이지 않는다
  • 알 수 있는 것은 경계에 수직인 방향의 움직임뿐이다
  • 모서리(corner)처럼 여러 방향으로 밝기가 바뀌는 곳은 움직임이 하나로 정해진다
  • 그래서 추적할 점은 모서리처럼 특징이 뚜렷한 곳을 고른다

설명 문틈으로 지나가는 긴 막대를 본다고 생각해 봅시다. 막대의 한 부분만 보이면, 막대가 오른쪽으로 갔는지 대각선으로 갔는지 구분할 수 없습니다. 막대의 길이 방향 움직임은 틈 안에서 아무 변화도 만들지 않기 때문입니다. 반면 막대의 끝(모서리)이 보이면 어느 쪽으로 갔는지 분명해집니다. 이것이 조리개 문제이고, "식이 하나 모자라다"는 것을 그림으로 보여 주는 예입니다.

예상 질문 Q: 벽처럼 무늬가 없는 곳은 어떻게 되나요? A: 밝기 변화가 거의 없어서 움직임을 구할 단서가 없습니다. 이런 곳의 Optical Flow 결과는 믿기 어렵습니다.

주의 이발소 간판 착시도 같은 원리로 설명됩니다. 화면에 보이는 움직임과 실제 움직임이 다를 수 있다는 점과 연결해 주면 좋습니다.

Lucas-Kanade: 특징점 추적 (Sparse)

  • 추가 가정: 작은 창(예: 주변 몇 픽셀) 안의 픽셀들은 같이 움직인다
  • 창 안의 여러 식을 함께 풀어 (u, v)를 구한다 (최소제곱)
  • 추적할 점 찾기: cv2.goodFeaturesToTrack (Shi-Tomasi 모서리)
  • 추적: cv2.calcOpticalFlowPyrLK → 새 위치와 추적 성공 여부(status)

설명 Lucas-Kanade(1981)는 "식이 하나 모자란" 문제를 이웃의 도움으로 풉니다. 점 하나 주변의 작은 창 안에 있는 픽셀들은 모두 같은 방향으로 움직인다고 가정하면, 픽셀 수만큼 식이 생기므로 u, v 두 값을 구할 수 있습니다. 조리개 문제 때문에 이 방법은 모서리 같은 점에서 잘 동작하므로, 먼저 모서리 점을 찾고 그 점들만 따라갑니다. 일부 점만 계산하므로 "Sparse(듬성듬성한) Optical Flow"라고 부릅니다.

예상 질문 Q: 추적하던 점이 사라지면 어떻게 되나요? A: 물체에 가려지거나 화면 밖으로 나가면 추적이 실패하고, 함수가 돌려주는 성공 여부(status)가 0이 됩니다. 실패한 점은 버리고, 남은 점이 적어지면 특징점을 다시 찾습니다.

주의 점은 시간이 지날수록 조금씩 어긋날 수 있습니다(드리프트). 오래 추적할수록 위치가 틀어질 수 있으니 주기적으로 점을 새로 찾는 것이 일반적입니다. 창 크기와 같은 인자의 기본값은 버전 확인이 필요합니다.

이미지 피라미드로 큰 움직임 다루기

  • 움직임이 크면 "작은 움직임" 가정이 깨진다
  • 이미지 피라미드(image pyramid): 이미지를 1/2씩 줄인 여러 층
  • 작은 층에서는 큰 움직임도 작아진다 → 작은 층에서 대략 구하고, 큰 층으로 내려오며 다듬는다
  • calcOpticalFlowPyrLK의 Pyr가 피라미드, 층 수는 maxLevel로 정한다

설명 지도를 볼 때 먼저 축소된 전국 지도로 대략적인 위치를 찾고, 확대하면서 정확한 위치를 찾는 것과 같습니다. 원본에서 20픽셀 움직인 점은, 1/2로 줄인 이미지에서는 10픽셀, 1/4로 줄이면 5픽셀만 움직인 것으로 보입니다. 가장 작은 층에서 대략적인 움직임을 구하고, 그 값을 출발점 삼아 한 층씩 크게 내려오면서 다듬으면 큰 움직임도 따라갈 수 있습니다. 이 방식을 coarse-to-fine이라고 합니다.

예상 질문 Q: 층을 많이 쌓을수록 좋나요? A: 더 큰 움직임을 다룰 수 있지만, 너무 작게 줄인 층에서는 특징이 뭉개져 오히려 틀릴 수 있습니다. 영상의 움직임 크기를 보고 정합니다.

주의 20, 10, 5픽셀은 설명을 위한 예시 숫자입니다. 피라미드는 Optical Flow뿐 아니라 여러 크기의 물체를 다루는 Object Detection 등에서도 나오는 일반적인 아이디어입니다.

Farneback: 모든 픽셀의 흐름 (Dense)

Sparse (Lucas-Kanade)
  • 고른 특징점만 계산
  • 출력: 점마다 새 위치
  • 가볍다. 점 추적, 궤적 그리기
Dense (Farneback)
  • 모든 픽셀의 (u, v) 계산
  • 출력: H x W x 2 배열
  • 무겁다. 움직임 영역, 흐름 지도
flow = cv2.calcOpticalFlowFarneback(prev_gray, gray, None,
                                    0.5, 3, 15, 3, 5, 1.2, 0)

설명 Farneback(2003) 방법은 모든 픽셀마다 움직임 벡터를 구합니다. 각 픽셀 주변의 밝기 모양을 간단한 2차 다항식으로 근사하고, 두 프레임에서 그 모양이 얼마나 옮겨 갔는지로 움직임을 추정합니다. 결과는 이미지와 같은 크기에 채널이 2개(u, v)인 배열이라서 "흐름 지도"라고 볼 수 있습니다. 모든 픽셀을 계산하므로 Sparse 방식보다 무겁고, 대신 움직이는 영역 전체를 볼 수 있습니다.

예상 질문 Q: 숫자 인자가 너무 많은데 다 외워야 하나요? A: 아닙니다. 피라미드 축소 비율, 층 수, 창 크기, 반복 횟수 같은 값이며, OpenCV 문서의 예제 값으로 시작해 필요할 때 창 크기 정도만 조절하면 됩니다.

주의 입력은 두 프레임 모두 흑백이어야 합니다. 화면의 예시 인자는 OpenCV 튜토리얼에서 흔히 쓰는 값이지만 권장값이 정해진 것은 아니므로, 각 인자의 의미는 버전별 문서를 확인합니다.

흐름을 색으로 표시하기

  • 벡터 (u, v)를 크기(magnitude)와 방향(angle)으로 바꾼다: cv2.cartToPolar
  • 방향 → 색상(Hue), 크기 → 밝기(Value), 채도는 최대로
  • HSV 이미지를 BGR로 바꿔 보여 준다. OpenCV의 H 범위는 0~179이므로 각도(도)를 2로 나눈다
  • 같은 색 = 같은 방향, 밝을수록 빠르다, 검은색 = 움직임 없음

설명 Dense Optical Flow는 픽셀마다 화살표가 하나씩이라 화살표로 다 그리면 화면이 새까매집니다. 그래서 색으로 바꿔 보여 줍니다. 방향은 색상환의 색으로, 빠르기는 밝기로 나타내면, 오른쪽으로 가는 사람은 한 가지 색, 왼쪽으로 가는 사람은 다른 색으로 칠해지고, 가만히 있는 배경은 검게 나옵니다. HSV 색공간에서 색상(H)과 명도(V)가 따로 있다는 점을 그대로 활용한 것입니다.

예상 질문 Q: 어떤 색이 어떤 방향인가요? A: 정해진 표준은 없고 변환 방식에 따라 달라집니다. 그래서 결과 옆에 색상환(방향 범례)을 함께 보여 주는 것이 좋습니다.

주의 크기는 0~255 범위로 정규화(cv2.normalize)해서 밝기에 넣습니다. 프레임마다 정규화하면 그 프레임에서 가장 빠른 곳이 항상 가장 밝게 나오므로, 프레임끼리 밝기를 비교하면 안 됩니다.

Optical Flow의 응용

움직임 방향
출입구에서 들어오는지 나가는지, 정해진 방향과 반대로 가는지 판단
움직이는 영역
흐름의 크기에 임계값을 주면 움직임 마스크가 된다
흔들림 측정
화면 전체가 같은 방향으로 움직이면 카메라가 흔들린 것. 흔들림 보정의 기초
점 추적
특징점의 궤적으로 물체가 지나간 경로를 그린다

설명 Optical Flow로 얻은 방향과 크기는 여러 판단에 쓰입니다. 출입구 영상에서 사람 영역의 흐름 방향을 보면 들어오는지 나가는지 알 수 있습니다. 흐름 크기에 임계값을 주면 배경 차분처럼 움직이는 영역을 얻을 수 있습니다. 화면 전체의 점들이 한꺼번에 같은 방향으로 움직였다면 물체가 아니라 카메라가 움직인 것이므로, 그 움직임을 반대로 보정하는 것이 흔들림 보정(stabilization)의 기본 아이디어입니다.

예상 질문 Q: 카메라가 흔들리는 영상에서 물체 움직임만 보고 싶으면요? A: 화면 전체의 대표 움직임(예: 점들의 이동량 중앙값)을 카메라 움직임으로 보고 빼 주면, 남은 움직임이 물체의 움직임에 가깝습니다.

주의 이 응용들은 개념 수준의 예입니다. 실제 시스템에서는 조명, 가림, 카메라 위치 같은 조건에 따라 추가 처리가 필요하므로 "Optical Flow만으로 된다"고 단정하지 않습니다.

속도 추정의 한계

  • Optical Flow가 주는 값은 픽셀 / 프레임이다
  • FPS를 곱하면 픽셀 / 초가 된다
  • 미터 / 초로 바꾸려면 픽셀 하나가 실제 몇 미터인지 알아야 한다
  • 그 값은 카메라와의 거리, 원근에 따라 화면 위치마다 다르다

화면 위 이동량을 실제 속도로 바꾸려면 카메라 보정(calibration)이나 기준 거리 같은 추가 정보가 필요하다

설명 "이 차가 시속 몇 km로 달렸나"를 Optical Flow로 바로 알 수는 없습니다. Optical Flow는 화면에서 몇 픽셀 움직였는지만 알려 주고, FPS를 이용하면 1초에 몇 픽셀인지까지는 계산할 수 있습니다. 하지만 같은 1미터도 카메라 가까이에서는 수백 픽셀, 멀리서는 수십 픽셀로 보이므로, 픽셀을 미터로 바꾸는 비율이 화면 위치마다 다릅니다. 그래서 도로의 차선 간격처럼 실제 길이를 아는 기준이나 카메라 보정 정보가 있어야 합니다.

예상 질문 Q: 그럼 과속 단속 카메라는 어떻게 속도를 재나요? A: 레이더 같은 별도 센서를 쓰거나, 정해진 두 지점 사이를 지나는 시간을 재는 방식처럼 실제 거리를 아는 조건을 이용합니다. 영상만으로 하려면 거리 기준이 꼭 필요합니다.

주의 이 밖에도 Optical Flow는 조명이 바뀔 때, 물체가 가려질 때, 무늬 없는 영역, 너무 빠른 움직임(흐림)에서 틀리기 쉽습니다. 이런 문제를 줄이려고 딥러닝으로 흐름을 추정하는 모델(예: RAFT, Teed & Deng, ECCV 2020)도 있다는 정도만 소개해도 됩니다.

[실습] 움직임 분석

Colab 열기 (준비 중)

이 실습이 다루는 개념:

1프레임 차분
이웃 프레임의 차이로 움직임 찾기
2배경 차분
MOG2, KNN 전경 마스크와 그림자
3마스크 후처리
모폴로지, 윤곽선, 박스
4Optical Flow
Lucas-Kanade 추적, Farneback 색 표시

설명 고정 카메라 영상 하나로 프레임 차분과 배경 차분을 비교하고, 마스크를 정리해 움직이는 물체에 박스를 그린 뒤, Optical Flow로 움직임의 방향을 보는 실습입니다. 학생들이 볼 것은 다음과 같습니다. 프레임 차분에서 물체 가장자리만 잡히는 모습, 배경 차분에서 그림자가 회색으로 표시되는 모습, 후처리 전후의 박스 개수 차이, Lucas-Kanade 궤적이 시간이 지나며 줄어드는 모습, Farneback 색 지도에서 방향마다 색이 다른 모습입니다.

주의 실행 팁: CPU 런타임으로 충분하지만 Dense Optical Flow는 프레임이 크면 오래 걸리므로, 시간이 많이 걸리면 프레임 크기를 줄이거나 앞부분 몇 초만 처리해 보게 합니다. 패키지 설치 후 재시작 안내가 나오면 따르고, 동영상 파일 경로가 맞는지 먼저 확인하게 합니다. 자세한 진행은 노트북의 설명 셀과 주석에 있습니다.

핵심 정리

설명 동영상의 구조와 처리 루프, 움직임 검출, Optical Flow의 핵심 개념을 정리합니다.

동영상 처리의 핵심

프레임과 FPS
동영상 = 프레임의 연속. 시간 = 프레임 번호 / FPS
코덱과 컨테이너
압축 방식과 파일 형식은 서로 다른 것
처리 루프
열기 → 읽기 → 처리 → 표시·저장 → 해제
입력 종류
파일, USB 카메라, RTSP 스트림을 같은 방식으로 읽는다
시간 예산
30 FPS면 프레임당 약 33ms
샘플링
간격을 두고 뽑고, 동영상 단위로 분할

설명 동영상은 이미지의 연속이고, 프레임 번호와 FPS로 시간을 알 수 있습니다. 파일 형식(컨테이너)과 압축 방식(코덱)은 따로 정해지며, 저장할 때는 코덱, FPS, 크기를 맞춰야 합니다. 실시간 처리는 프레임당 시간 예산 안에 들어와야 하고, 학습 데이터를 만들 때는 간격을 두고 뽑아 동영상 단위로 나눕니다.

예상 질문 Q: 파일로 만든 코드를 카메라로 바꾸려면 무엇을 고쳐야 하나요? A: 열 때 넘기는 값(경로 대신 장치 번호나 RTSP 주소)만 바꾸면 루프는 그대로 쓸 수 있습니다. 대신 끝이 없는 입력이므로 종료 조건과 처리 시간을 챙겨야 합니다.

움직임 분석 기법 비교

기법알 수 있는 것전제주의할 점
프레임 차분바뀐 곳고정 카메라가장자리만, 멈추면 사라짐
배경 차분 (MOG2, KNN)전경 영역고정 카메라조명 변화, 그림자, 멈춘 물체
Lucas-Kanade (Sparse)특징점의 이동밝기 항상성, 작은 움직임모서리 필요, 점 손실
Farneback (Dense)모든 픽셀의 이동밝기 항상성, 작은 움직임연산량, 무늬 없는 영역

설명 네 가지 기법은 "무엇을 알고 싶은가"에 따라 고릅니다. 움직인 영역만 알면 되면 차분 계열, 방향과 크기가 필요하면 Optical Flow입니다. 몇 개의 점을 오래 따라가려면 Lucas-Kanade, 화면 전체의 흐름이 필요하면 Farneback을 씁니다. 모두 학습 데이터 없이 바로 쓸 수 있지만, 각자의 전제(고정 카메라, 밝기 항상성)가 깨지면 결과도 틀어진다는 점이 공통입니다.

예상 질문 Q: 딥러닝 Object Detection이 있는데 이런 기법을 왜 배우나요? A: 학습 없이 가볍게 쓸 수 있고, 검출기를 언제 돌릴지 정하거나(움직임이 있을 때만), 검출 결과의 움직임 방향을 구하는 등 딥러닝과 함께 쓰이는 경우가 많기 때문입니다.

주의 표의 내용은 일반적인 경향입니다. 영상과 인자 설정에 따라 결과가 달라지므로, 어떤 기법이 항상 낫다고 말하지 않습니다.
